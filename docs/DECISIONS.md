# Decision log

This log records the architectural and product decisions behind ancora, with the reasons and the alternatives weighed at the time, newest first. Entries that a later decision replaced are kept for history and marked as superseded, with the date and subject of the entry that replaced them.

| Date | Decision | Why | Alternatives considered |
|------|----------|-----|-------------------------|
| 2026-11-15 | Pilot applications go by email to the maintainer instead of a public GitHub issue. | Organizations describing their finances and plans should not have to do so in public, and a mailto link needs no off-chain storage. A pilot address on ancora's own domain replaces it once the project has one. | A public GitHub issue (the 2026-11-04 approach) |
| 2026-11-15 | The off-chain records are backed up nightly as encrypted JSON in a GitHub Actions artifact kept for 90 days. | Neon's free plan keeps six hours of history. JSON read through the app's own driver does not depend on Neon's Postgres version and restores idempotently (`on conflict do nothing`); it is encrypted because any GitHub user can download a public repository's artifacts. The backup is a copy, not new off-chain data. | `pg_dump`; a paid Neon plan |
| 2026-11-15 | The Circle USDC test float refills itself by selling a Friendbot account's XLM on the testnet XLM/USDC liquidity pool, paid straight to the operator; EURC stays hand-filled. | Circle's faucet is captcha-gated, so the float was empty most of the time. Friendbot XLM costs nothing and the operator's own XLM is never sold; the refill accepts only Circle's testnet USDC and refuses a pool holding under 1,000 USDC. Testnet has no EURC liquidity. | Topping up by hand at Circle's faucet (the 2026-10-26 approach) |
| 2026-11-12 | ancora's off-chain records (discussions and reactions, the scheduler's organization list, registry names, push subscriptions, pictures) move from Vercel Blob to one Neon Postgres database, and `@vercel/blob` is removed. | Blob bills these small, frequently changed records per operation and blocks the store once the monthly allowance is spent. Rows make concurrent posts plain inserts, and one query replaces a listing plus fetches. Pictures (at most 300 KB, content-addressed, served by `/api/image` with a long CDN cache) move too, so there is one store, one secret and one backup. | Vercel Pro (keeps per-operation billing); Blob for pictures only (two stores); Upstash Redis (no relations); reading the organization list and registry names from the chain (still planned, see ROADMAP) |
| 2026-11-12 | After Blob blocked the store, discussions become one ETag-guarded JSON file per organization, loaded only when a screen with requests opens, and the site-wide default data source becomes the `DEFAULT_DATA_SOURCE` env var instead of the `/admin` switch. Discussion storage superseded by 2026-11-12 (Neon Postgres); on-demand loading and the env-var default still apply. | Every open app read every organization's discussions twice a minute as a listing plus one fetch per entry, which exhausted the quota and took registry names, the scheduler index and the demo setting down with it. The default data source changes rarely, so a redeploy is acceptable and visits stop costing a read. | Vercel Pro; the per-entry layout with lazy loading only; Edge Config for the demo setting |
| 2026-11-04 | The BlendUSDC test float refills itself from Blend's testnet faucet whenever a grant leaves it below 500. | End-to-end runs and demos drained the float until grants shrank to a few dollars and flows that need funds failed. It uses the setup script's faucet mechanism, checked to pay exactly the accepted token. | A scheduled refill (no room under the twelve-function limit); topping up by hand |
| 2026-11-04 | The landing page presents use cases as labelled, illustrative scenarios with fictional organizations under a "Preview" bar; pilot applications go to a GitHub issue. Pilot channel superseded by 2026-11-15 (pilot applications by email). | ancora has no customers yet, and presenting invented results as real would mislead visitors. GitHub was the one contact channel that needed no database or mail service. | Case studies with invented results; a waitlist form (needs storage or a mail provider) |
| 2026-11-03 | The UI is translated with a small in-house `t()`: the English text is the key, a German catalog (formal "Sie") translates it, and a test requires a German entry for every text used. | Two languages with plain strings need no library, English keys keep the code readable, and screens can be translated one at a time. The language starts from the browser's, is kept per browser, and money and dates follow it. | i18next or FormatJS (justified by more languages or plural rules); symbolic keys such as `nav.overview` |
| 2026-11-02 | Device keys are derived from the passkey's PRF secret (HKDF-SHA256, fixed salt) when it has one, random otherwise; a restore keeps a derived key only where it matches the published one. | Synced passkeys reach a new phone without any action, so derived keys come back with nothing stored anywhere. Matching the published key ensures keys made earlier at random, or by a passkey without PRF, never replace a working key; Chromium's virtual authenticator supports PRF, so end-to-end tests cover it. | A PRF-encrypted backup stored on-chain (keyring change and redeploy); making existing keys passkey-bound (every member would have to re-share) |
| 2026-11-02 | Private details use a separate keyring contract and device-held X25519 keys; each epoch's organization key is wrapped per member in the browser. Key generation refined by 2026-11-02 (device keys from the passkey's PRF secret). | A separate contract works for every organization without an upgrade, and the organization contract is near its size limit. Device keys need no second biometric prompt and run in end-to-end tests; a new device gets access when another member shares the key. | Keys from the passkey's PRF extension (extra prompt, not on Windows 10, untestable with the virtual authenticator at the time); hiding amounts now (no ready circuits for rules over hidden amounts) |
| 2026-11-02 | Each device keeps an encrypted snapshot of the confidential pot (openings, history, last ledger read) and replays only newer events. | RPC keeps about a week of events and the pot's openings exist only off-chain. The snapshot is encrypted with a key derived from the viewing key and never trusted alone: the replay must reproduce the commitments on-chain. | A durable event archive (a service to run; still the answer for new devices); an encrypted snapshot in the keyring (one more signature per step) |
| 2026-11-02 | The confidential pot runs on ancora's own deployments of OpenZeppelin's confidential token, verifier and auditor registry, with no hooks and no admin, and ancora writes its own browser client to the OZ SDK specification. | OZ's examples include admin freeze, clawback and key-rotation roles that would let the operator take or lock funds. No JavaScript client exists for the 0.8.0 circuits, and the npm builds of the pinned toolchain reproduce the verification keys byte for byte, so proofs made in the browser verify. | OZ's compliant token with ancora holding the roles (custodial); the community SDK (older circuits); waiting for an official client |
| 2026-11-02 | Blob reads are cached briefly per function instance, organization markers are written only when missing, and an unreadable demo setting falls back to `DEFAULT_DATA_SOURCE`. Superseded by 2026-11-12 (Blob redesign) and 2026-11-12 (Neon Postgres). | The Hobby plan's Blob operations ran out because every visit read the demo setting uncached and every organization load listed its discussions and rewrote its marker, which dropped the site to sample data. | Global Config for the demo setting; a database |
| 2026-11-02 | `pnpm-lock.yaml` is excluded from Biome. | It is generated by pnpm, and pnpm and Biome disagree on quoting, so every dependency change rewrote the whole file. | Formatting the lockfile after every install |
| 2026-11-02 | Lifeline's inactivity path and succession live in the organization contract (last activity per member, successor per position). | The recovery contract has no upgrade path and its address is fixed in every organization; positions are what matter, and only the organization knows who acted. | A new recovery contract (existing organizations would stay on the old one); a heartbeat policy on the person's smart account (not offered by the kit's accounts) |
| 2026-11-02 | The organization contract checks the quantum-safe seal against the member's registered ML-DSA key, using a verifier chosen by governance. | It needs nothing from smart-account-kit, whose external-signer signing could not be verified, and works the same for every member; the organization's rules decide whether passkey seals still count. Governance chooses the verifier so a member cannot register one that accepts anything. | An OZ external signer on a seal-only context rule (context rules scope by contract, not function) |
| 2026-11-01 | New organization state goes under new storage keys (`Allowances`, `Recipients`, `FxOracle`, `Releases`); stored structs (`Policy`, `SpendingLimit`, `OrgInfo`, `Evaluation`) never change shape. | An organization that moves to a new release keeps its storage, and a changed struct would no longer decode. | Migrations on upgrade (none exist yet) |
| 2026-11-01 | Exchange rates from Reflector's Pulse forex oracle (SEP-40) set only the tier and seal of other-currency payments; budgets and the general allowance count in the rules' currency, and per-asset allowances use the asset's own units. | Booking a budget at one rate and releasing it at another would drift, and asset allowances need no rate. Pulse is free on testnet; Reflector's Beam oracle needs paid access per caller. | Converting budgets at the booking rate and storing it per request (changes stored request types) |
| 2026-11-01 | Deals are a separate contract with no admin and no upgrade path; an organization takes part only through requests under its own rules. | Organizations have no `__check_auth`: their consent is the organization contract calling after its approvals, so the deal contract needs no copy of the rules and works for any Stellar party. Without an admin ancora can never move deal funds; a new version is a new deployment. | `__check_auth` on organizations (a large redesign); one deal contract per pair; an upgradable deal contract with an ancora admin (custodial) |
| 2026-11-01 | Organizations upgrade only through their own governance (`Change::Upgrade`), and only to the latest `ancora-organization` release on the Stellar Registry they were deployed with. | Organizations get new features without being recreated while staying non-custodial: the operator can publish a release but cannot make any organization run it. Approvers approve one exact, publicly checkable hash, and a newer release published in between makes the change fail. | Operator-triggered upgrades (custodial); any hash the members approve (approvers can't judge arbitrary code); an ancora-run release list in our registry (a redeploy would orphan every organization) |
| 2026-11-01 | Server transactions use eight channel accounts whose keys are derived from the operator's secret, with the operator as operation source and fee-bump payer; missing channels are created on first use. | Stellar Core keeps one pending transaction per source account, so a single operator source serialized every server transaction. Fee bumps keep each channel at its 1.5 XLM reserve, and derived keys add no secret to manage. | Channels funded with their own XLM (hundreds of XLM each for testnet rent); separate channel secrets in env vars |
| 2026-10-28 | Routes that belong together share one function, and a test enforces at most twelve functions. | Vercel's Hobby plan refuses deployments with more than twelve functions only after a green build, which once left production on an old version unnoticed. | Vercel Pro (cost before revenue); one catch-all router (loses per-route settings such as `maxDuration`) |
| 2026-10-28 | Custom roles are one governance change that replaces the ranked role list (`SetRoles`) with the new rules-document hash; roles are ids with derived labels, and a `version()` view tells the app which organizations support it. | Members hold roles by id in OpenZeppelin AccessControl, so adding, reordering and dropping empty roles needs no member migration, and one change keeps approvals, the lock-out guard and the document hash together. Renaming is add, move, remove; the view avoids guessing support from errors. | On-chain display names per role; a separate role registry contract; editing roles inside `UpdatePolicy` |
| 2026-10-28 | The address book lives in the organization contract, editable by any member without approvals. | Every member must see the same name for an address without a server in between, and a later "pay only saved recipients" rule needs the list where rules are enforced. Saving a name is not a rule change; names are public on-chain like the rest of the account. | Off-chain storage next to discussions (a server and another function); per-device lists |
| 2026-10-28 | Web push is triggered by the relayer after a successful transaction; messages carry only facts that are public on-chain, so subscribing needs no proof of the pass. | The relayer already sees every signed organization action, so no trigger route or indexer is needed and only confirmed actions notify. A device subscribed to someone else's ancora ID learns nothing that isn't already public. Wallet deposits don't pass the relayer and are not notified yet. | Polling RPC events from a cron (minutes of delay, daily Hobby cron); signed subscriptions (needed if messages ever carry private data) |
| 2026-10-28 | Monthly statements are a print-styled page the browser saves as PDF, showing money in, money out, net and today's balance rather than opening and closing balances. | No PDF library to ship or audit, and the text stays selectable. Testnet RPC exposes about a week of deposits, so a reconstructed opening balance could be wrong, while listed totals and the token balance are exact. | A PDF library (jsPDF, pdfmake); server-rendered PDFs (uses a function slot); reconstructed opening balances |
| 2026-10-28 | Batch payments are one request kind in the organization contract, judged on their total and paid out atomically. | One approval for a payroll and never a half-paid payroll: either all transfers run or the request stays approved and can be sent again. The batch needs whatever its total would need, and any new recipient makes the batch new. | Separate requests per line; per-line approval; secure handover for batches |
| 2026-10-28 | Payment links are paid through the organization contract (`pay_link`), which pulls the amount from the payer's wallet and records the payer. | Soroban token transfers carry no memo, so matching plain transfers to invoices would be guesswork; the contract records exactly who paid and lets each payer pay once. Payers need any Stellar wallet, no ancora pass, and pay their own fee. | Plain transfers matched off-chain; a separate invoicing contract |
| 2026-10-26 | Activity is read from the ledger's token events (RPC `getEvents`) in chunks and kept per organization on the device, without an indexer or database. | The list must show what actually happened to the money, including deposits the app never saw, each linked to a transaction. RPC keeps about a week, so the device keeps older entries; the data is public, so storing it locally carries no trust. | A hosted indexer (Mercury, SubQuery) or own event store; Horizon (no contract-side history); entries derived from requests only (misses deposits) |
| 2026-10-26 | ancora serves its own smart-account index for the passkey kit (schema 2), built from Mercury's candidate list plus each wallet's creation transaction read from the ledger. | The kit refuses a passkey whose wallet creation it cannot verify, and Mercury returned ancora's wallets as `missing_birth`, breaking sign-in on new devices and after session expiry. The kit still verifies against the chain; the index only points at the transaction. | Disabling the indexer (only the creating device could sign in); recording wallet creation off-chain from the relayer |
| 2026-10-26 | Standing orders live in the organization contract; each run re-proposes the payment from the member who set it through the ordinary payment path, anyone may trigger a due run, and missed runs are skipped. | The member's signature on the schedule is the standing authorization, while current limits, tiers, budgets and funds still decide every run, so a schedule can never exceed a one-off payment. Skipping missed runs avoids a burst of payments; only organizations on the new Wasm get the feature. | An off-chain scheduler signing with a server key (the operator would become a signer); catching up missed runs; a separate scheduler contract |
| 2026-10-26 | Standing orders are run by a daily Vercel cron over an index of organizations, one marker per organization written at deployment and when the app opens it. Index storage moved from Blob by 2026-11-12 (Neon Postgres). | The registry cannot list all organizations, and changing it would orphan every organization; markers cost nothing and rebuild through use. Daily runs suit weekly to monthly orders and the Hobby cron. | Enumerating `register_org` events (RPC keeps a week); a global list in a new registry version |
| 2026-10-26 | Organizations register their treasury name in the Stellar Registry's open (unverified) channel, signed by the top role's pass; ancora stores the chosen name per organization and verifies it against the registry on read. Name storage moved from Blob by 2026-11-12 (Neon Postgres). | The verified root channel needs the registry manager's signature, the open channel accepts any owner. The registry resolves name to contract but not back, so the settings page needs the name stored; registering with the person's pass makes them the owner, matching who may change the profile. | Registering with the operator key (ancora would own every name); a verified-channel name |
| 2026-10-26 | ancora's contracts are distributed through the Stellar Registry as named, versioned Wasm releases, starting with a publish script and a dry run. | A published release lets anyone check that an organization runs exactly the code ancora released, instead of trusting the operator's env var. It is the same ecosystem as perch, so the two adoptions line up. | The Wasm hash only in the operator's env; a self-hosted release page |
| 2026-10-26 | Secure handover is a flag on a payment in the organization contract: held after approval, paid out on two confirmations, cancellable by the sender's side. | The money stays under the organization's control until both sides agree, so no third contract holds funds and approvals, budgets and committed funds apply unchanged. The recipient confirms with their own pass; a link carries the organization and request id because the registry indexes memberships, not payees. | A standalone escrow contract (funds outside the rules); an on-chain recipient index (a registry redeploy would orphan every organization) |
| 2026-10-26 | The headline total converts currencies with ECB reference rates (Frankfurter API, URL in config), for display only, with a labelled fixed fallback. | People want one number for what the organization holds, and a labelled reference rate is enough for that. The rules never use this rate, so no approval is weakened by a web rate. | Reflector's testnet oracle (address not confirmed at the time); no conversion |
| 2026-10-26 | Budgets are part of `Policy` in the organization contract, enforced as hard or soft, booked at proposal and released on decline. | Budgets become rules under one governance path (`UpdatePolicy`) and one document hash. Booking at proposal mirrors committed funds, so several open requests cannot overspend; hard budgets refuse other-currency payments and soft budgets flag them. | A separate budget contract; per-member limits per category; counting at execution |
| 2026-10-26 | ancora follows perch's document discipline (canonical JSON per CANON v1, plain SHA-256 `doc_hash` on-chain, compiler layering) without depending on it; the organization contract stays the evaluator. | Perch (Apache-2.0, pre-audit) models per-signer rights on an OZ account but has no roles, amount ranges, approvals collected over time, objection windows, seals or budgets, and its caps reset when a rule changes. Aligning the format makes a later migration a lowering step, not a rewrite. | Depending on perch now; keeping our own canonical form |
| 2026-10-26 | Lifeline recovers a person's positions: each organization hands the member's role and limit to a new pass, authorized by the `ancora_recovery` contract named at the organization's deployment. | A contract signer's authorization path on the kit's accounts is unverified and their rules scope by contract, not function. The money sits in organizations, so moving positions restores what matters and removes the lost pass everywhere; the old pass can cancel until the waiting period ends, and finishing needs no signature, so the operator can submit it. | A delegated recovery signer on the account (later; would also recover the account's own balance); recovery votes inside each organization |
| 2026-10-26 | Budgets are off-chain plans in Vercel Blob, one file per organization, categorized by a hashtag in the on-chain payment reference. Superseded by 2026-10-26 (budgets in `Policy`). | A budget informs while the rules enforce; keeping plans out of the contract kept it small, and spend is still read from on-chain requests. Hashtags need no new contract field. | Budgets enforced in the contract; a separate ledger database |
| 2026-10-26 | Bank deposits and withdrawals go through SEP-24 anchors, with the person's own wallet as the SEP-10 identity rather than the organization contract. | SEP-10 authenticates classic accounts by key; the organization is a contract, and a passkey account would need SEP-45, which anchors don't support yet. Deposits land in the wallet and move on via wallet funding, and a withdrawal becomes an ordinary payment request under the rules. | SEP-45 once anchors support it; Bridge or a licensed euro anchor for real money (needs KYB) |
| 2026-10-26 | Spending limits live in the organization contract (`SetSpendingLimit`, rolling window per member, checked in `propose_payment`), not in OpenZeppelin's `spending_limit` policy. | OZ's policy guards a smart account's own transfers, but the money sits in the organization contract, which is not a smart account. Any address that can authorize can be a member, so a member with a limit serves as an automation key. | The OZ policy on each person's account (caps the person, not the organization); a separate allowance contract |
| 2026-10-26 | Discussion threads are append-only Vercel Blob files, one per entry, reaction and "answered" mark, with organization and membership checked against the contract. Superseded by 2026-11-12 (Neon Postgres). | Text stays private to the organization and off the ledger, and one file per fact avoided lost updates on concurrent posts. Signing entries (SEP-53) is the follow-up for provable authorship. | A database; on-chain comments; no membership check |
| 2026-10-26 | The organization logo is a URL on the organization contract (`set_logo`, top role, no approval), pointing at the same content-addressed image store as profile pictures. | A logo is cosmetic and should follow the organization to every device, and reusing the image store keeps one upload path. | Logo changes as governance requests; logos in the registry |
| 2026-10-26 | Funding from a person's own wallet goes through Stellar Wallets Kit (Freighter, Hana, xBull and Albedo modules only), with ancora building the token `transfer(wallet → organization)` invocation for the wallet to sign. | A wallet's plain send is a classic payment, which cannot target a contract address; building the Soroban invocation works with any wallet that signs transactions. Importing four modules on demand keeps hardware-wallet and WalletConnect SDKs out of the bundle. | Freighter only; a deposit address per person (custodial); SEP-24 ramps for crypto deposits |
| 2026-10-26 | Seal test vectors come from `@noble/post-quantum`, the library the app uses on the device, and live in `contracts/test-vectors/ml-dsa-44.json`. | They prove the browser's signer and the on-chain verifier interoperate, kept next to the rules vectors. | Rust-generated vectors only |
| 2026-10-26 | The quantum-safe seal is verified by an in-contract ML-DSA-44 verifier (`fips204` 0.5, no_std) behind OpenZeppelin's external-verifier interface. Where the seal is checked superseded by 2026-11-02 (seal checked by the organization contract); the verifier remains. | Testnet then ran protocol 29, without an ML-DSA host function; the pure-Rust verifier compiles to 15 KB of Wasm and verifies within testnet limits, checked on-chain. ML-DSA-44 is the smallest parameter set with 128-bit post-quantum security, and a native host function can later replace the body of `verify` without changing callers. | ML-DSA-65 (larger signatures, more CPU); waiting for the host function; a server-side check (not non-custodial) |
| 2026-10-26 | An asset's DeFindex vault is part of its allowlist entry (`Symbol:token:currency[:vault]`), fixed when the asset is accepted. | Which vault an asset earns in is a trust decision the operator makes per deployment, and the organization accepts it together with the asset through governance. | A vault registry; founder-chosen vaults |
| 2026-10-26 | Earnings are shown as vault value minus principal moved in, tracked per token in the organization contract, with no rate figure on testnet. | The vault reports value per share, not a rate, and Blend's rate varies while the vault takes fees, so the honest number is what the organization would get back today against what it put in. | Quoting a rate from Blend's pool; the sample data's fixed simulated rate |
| 2026-10-26 | The Reserve is the organization contract depositing into the asset's DeFindex vault itself, pre-authorizing only the vault's token pull, and withdrawing by burning the shares worth the requested amount with a 1% tolerance. | The organization is a contract and cannot sign; invoker auth covers the direct vault call and one explicit sub-invocation covers the nested transfer, nothing else. Rounding happens in the vault's share math, so the withdrawal accepts at least 99% and the UI reads the exact value back. | Depositing through the person's account (the person would become the depositor); a separate treasury contract |
| 2026-10-26 | Non-fungible holdings (membership cards, certificates) are an outlook item; the asset list is typed for fungible tokens. | The asset model extends to OZ NonFungible contracts, but the rules engine compares amounts, which NFTs don't have. | Modeling NFTs now |
| 2026-10-26 | The Circle USDC test float is filled by hand at Circle's faucet, and test-money grants shrink to a tenth of what remains when the float runs low. Superseded by 2026-11-15 (automatic Circle USDC refill). | Circle's faucet is captcha-gated, so the setup script can only add the trustline and report; adaptive grants stretch one top-up across many demos. | Dropping Circle USDC; a larger manual float |
| 2026-10-26 | The assets an organization may accept come from an operator allowlist (`ORG_ASSETS`: symbol, contract, currency) resolved by the setup script; on testnet BlendUSDC and Circle USDC. | It keeps testnet to tokens with a faucet and a known issuer; the contract accepts any Stellar asset contract, so adding EURC is one config line. | Free-form token addresses in the UI (typos, scam tokens) |
| 2026-10-26 | Rules are written in one home currency per organization (EUR or USD, part of the policy document), and a payment in another currency takes the strictest tier plus the seal. Tier rule for other currencies superseded by 2026-11-01 (exchange rates set the tier and seal). | Tiers in two currencies would double the rules UI, and equating €1 with $1 would misapply the tiers; "strictest until a rate exists" can never under-approve. | Tiers per currency; fixed parity; an oracle immediately (an oracle outage could block payments) |
| 2026-10-26 | An organization holds a list of accepted stablecoins, each tagged with the fiat currency it stands for; balances, committed amounts and payments are per token, and accepting or dropping a token is a governance change (dropping needs a zero balance and no open request). | Organizations need to accept several stablecoins (Circle USDC, BlendUSDC, later EURC), and the contract already took one token at creation, so a list was the natural extension. | One token per organization; one organization per asset |
| 2026-10-25 | "Send now": the operator executes a fully approved request whose objection window has passed when any member asks; the contract re-checks everything, and the operator cannot create, approve or alter requests. | Nobody should have to pay or sign to let an approved payment leave, and the operator already sponsors fees. | Requiring a member's passkey for execution; a cron job |
| 2026-10-25 | Recovery ("Lifeline") goes through a dedicated recovery contract that is the only party allowed to change the account's signers, with a waiting period and cancellation by any signer; it can never move money. Superseded by 2026-10-26 (Lifeline recovers positions). | OZ context rules scope by contract, so guardians must not get a rule on the account itself; a delay plus cancel keeps a compromised guardian set from taking over silently. | Guardians as direct signers; social recovery without a delay |
| 2026-10-25 | Personal settings live on the person's page `/app/me`; `/app/settings` belongs to the organization (logo, on-chain facts). | Two subjects, two pages; the personal page doubles as what a person shows to get invited (ID, QR code). | One mixed settings page |
| 2026-10-25 | Profiles are on-chain in the registry (name up to 64 bytes, picture URL up to 256 bytes); pictures are content-addressed 256×256 WebP images uploaded without login, and only the owner's passkey can point their profile at one. Picture storage moved from Blob by 2026-11-12 (Neon Postgres). | A profile must follow the person to every device and organization, while the image is too large for on-chain storage; content addressing makes uploads idempotent and uninteresting to abuse. | Data URLs on-chain (rent); browser-only profiles; an account database |
| 2026-10-25 | ancora follows perch's idea (a declarative policy IR lowered onto OZ stellar-accounts) without depending on it, using stock OZ policies where they fit and custom rules in the organization contract where they don't. Spending limits superseded by 2026-10-26 (spending limits in the organization contract); perch alignment refined by 2026-10-26 (perch document discipline). | Perch's constraints are per call, while approvals with tiers and objection windows need state the organization contract owns anyway. The OZ `Policy` trait only needs `smart_account.require_auth`, which the organization contract satisfies as direct invoker. | Building on perch now (early project); re-implementing spending limits |
| 2026-10-25 | The rules are a declarative policy document (canonical JSON, `app/shared/policyDocument.ts`) compiled into the contract's `Policy`, and the contract stores the document's SHA-256 at creation and with each rule change. | Anyone can verify that the readable rules match what the contract enforces; the hash is cheap on-chain, and the document can be reproduced from contract state. | Storing the document on-chain (rent); no verification |
| 2026-10-25 | One passkey per person and one contract per organization: a person is an OpenZeppelin smart account (its address is the ancora ID), an organization is ancora's own `ancora_organization` contract, and one `ancora_registry` indexes profiles and memberships. | A person can hold several positions in several organizations with one passkey. Soroban's direct-invoker rule lets the person's account authorize calls on the organization, and the organization authorize token transfers and registry updates, without nested delegation; the organization contract can enforce tiers, four-eyes and objection windows, which an OZ policy on a shared smart account could not express. | One OZ smart account per organization with a passkey per member (rules only in the app); a shared multisig with each person's passkey added (nested auth, no on-chain rules) |
| 2026-10-25 | Site default is the Stellar testnet, with sample data as the automatic fallback. | The product should be shown working on-chain; the fallback and the Settings switch keep the demo usable. | Sample data by default with an opt-in |
| 2026-10-25 | The API functions accept any same-origin request plus an allowlist, and all other project hosts redirect to `ancora-gray.vercel.app`. | Requests through a deployment URL were refused by the relayer's Origin check; same-origin is always ours, and one canonical host keeps passkeys on one RP ID. | Listing every alias; no redirect |
