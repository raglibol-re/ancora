| 2026-10-25 | No pnpm workspace; `app/` is a standalone package, `contracts/` is Cargo-only | Nothing is shared between JS packages yet; keeps Vercel and CI simple | Root pnpm workspace |
| 2026-10-25 | No database | Testnet is the source of truth; logos go to Vercel Blob; UI preferences to the browser | Vercel-integrated Postgres/KV |
| 2026-10-25 | `vite-plugin-pwa` (Workbox) for manifest + service worker | Maintained, standard; avoids a hand-written service worker | Hand-written SW |
| 2026-10-25 | Theme tokens use CSS `light-dark()` with `color-scheme` | Each color defined once; `[data-theme]` override needs no duplicated dark block | Duplicated dark values under media query + attribute |
| 2026-10-25 | Fonts self-hosted via `@fontsource` | Works offline in the PWA; no third-party font requests | Google Fonts CDN |
| 2026-10-25 | Biome as the single formatter + linter | One fast tool, zero-warning policy is easy to enforce | ESLint + Prettier |
| 2026-10-25 | Production domain `ancora-gray.vercel.app` (passkey RP ID) | `ancora.vercel.app` is taken; the RP ID must stay stable or existing passkeys stop working | Custom domain later (would require re-enrolling passkeys) |
| 2026-10-25 | A higher role can fill a lower role's approval slot (treasurer counts as a board member, lead as a member) | Otherwise the club treasurer and company finance role could never approve anything; matches "at least" intuition | Exact-role matching only |
| 2026-10-25 | New-recipient approvals merge per role by keeping the higher count (spec wording), not by adding | Spec says "merge per role, keep the higher count"; so for the company, the new-recipient director only changes tier 0 | Additive (+1 on top of the tier) |
| 2026-10-25 | The strictest tier is the last tier; governance (members, rules, template) uses it without the seal | Templates are monotonic; one clear definition that the contract can mirror | Computing the "largest" requirement set |
| 2026-10-25 | Setup phase = the founder's own change requests could never complete (strictest tier unsatisfiable without the founder); founder-only, covers all governance changes | Mirrors choosing initial signers at account creation; also lets a lone founder adjust rules before inviting people | Member additions only; any member |
| 2026-10-25 | Changes that would make the strictest tier unsatisfiable are refused ("would lock the account") | Prevents an org from locking itself out of its own funds | Allow and warn |
| 2026-10-25 | Requests snapshot their evaluation at creation | Predictable for approvers; rule changes don't retroactively alter requests in flight | Re-evaluate on every approval |
| 2026-10-25 | Shared test vectors as JSON in `contracts/test-vectors/` | One language-neutral source both the TS engine and the Rust contracts test against | Duplicated fixtures per language |
| 2026-10-25 | One `DataSource` interface (snapshot + commands) with a sample adapter that runs every command through the domain engine | Features stay identical when the testnet adapter lands; sample mode is a faithful demo fallback, not a mock | Separate mock UI; per-feature fetchers |
| 2026-10-25 | Sample state persisted in localStorage; a "Viewing as" person switcher in sample mode | Demo survives reloads and shows both sides of four-eyes approval; replaced by passkey sign-in on testnet | In-memory only; fake login |
| 2026-10-25 | Moving money between the main account and the Reserve needs no approval; allowed for the top role and anyone who can approve the strictest tier | Money never leaves the organization; one-tap UX | Treat as a payment with approvals |
| 2026-10-25 | Requests get a `failed` status with a reason | Execution can fail (network, change no longer applies); demo admin retries it (task 13) | Reuse `declined` |
| 2026-10-25 | Logos resized in the browser to 256×256 WebP and kept in the sample state until Vercel Blob + org registry (task 11) | Same validation and UX now; storage swaps later | Wait for Blob before building the UI |
| 2026-10-25 | Request discussions (task 16) stay off-chain, with an optional on-chain hash per approval | Content isn't money and should stay private to the org; on-chain storage would be public and costly. The hash keeps "what did the approver see" verifiable | Fully on-chain comments; browser-only |
| 2026-10-25 | `app/.env.testnet` is generated by `scripts/setup-testnet.sh` and committed; the app builds with `vite --mode testnet` | Only public IDs; Vercel and CI build against exactly the deployments the script verified; no hand-copied env vars | Vercel env vars per ID; gitignored file |
| 2026-10-25 | BlendUSDC float is claimed from Blend's testnet faucet by the script (issuer-signed envelope, co-signed by the deployer) | Removes the manual faucet step from setup and after testnet resets; same mechanism blend-ui uses | Manual claim in the Blend UI with an imported key |
| 2026-10-25 | Reuse smart-account-kit v0.8.0's testnet verifiers, policies and relayer proxy | Audited OZ-based deployments that the kit is tested against; nothing to maintain | Deploying our own copies now |
| 2026-10-25 | Adopt the final brand handoff (`design/brand`): shield-and-anchor mark, size-cut icons, Brass Deep `#A8832F`, Dashboard dark surfaces; separate `--color-accent-text` for brass text | Matches the approved mark and its contrast rules; brass marks and brass text need different values to stay ≥ 4.5:1 | Keep the placeholder mark |
| 2026-10-25 | Keep Fraunces (headlines, amounts) + IBM Plex Sans (UI); don't adopt the exploration boards' Cormorant/Inter or the Nocturne system | The brief and the final wordmark specify Plex Sans; Identity/Dashboard boards are earlier rounds (their parchment light theme is deprecated in the handoff); Nocturne is the design tool's canvas system | Switch to Cormorant + Inter + Plex Mono |
| 2026-10-25 | The relayer (`/api/relay`) pays fees itself from the demo operator key, refilled by Friendbot (helper key merged into the operator, 10,000 XLM each) | Measured: a passkey transaction costs ~20–50 XLM on testnet today. Two causes, neither in our code: (1) testnet Soroban state (4.07 GB, rising) is above its 4.0 GB rent target, so rent is 2,271,304 stroops/KB vs 1,000 on mainnet; (2) the OZ smart account extends every storage entry to a 30-day TTL on each read, so the first use after deployment re-rents the whole account. OpenZeppelin Relayer Channels caps a key at 100 XLM/day, which two transactions exhaust | Keep Channels (mainnet plan, where the same ops cost well under 1 XLM); fork the OZ account to shorten the TTL extension (rejected: loses the audited deployment, deploy rent stays) |
| 2026-10-25 | The site-wide demo mode lives in Vercel Blob (`demo/state.json` in one public store `ancora`, read with `useCache: false`) | The one piece of state every visitor must share (which data source judges get by default) can't live on-chain or in a browser; Blob is already planned for logos (task 11) and needs no schema; origin reads make a switch immediate | Edge Config (writes need a Vercel API token); env var + redeploy; a database |
| 2026-10-25 | Fallback to sample data is decided in the browser from `/api/health` (site mode + RPC reachability, 4 s timeout), never silently: the banner shows the reason and a retry | Protects the demo video and judging if the testnet or the relayer is down, without hiding that sample data is shown | Server-side rewrite; no fallback |
| 2026-10-25 | The Functions accept any same-origin request (Origin host = request host) plus the allowlist; all other project hosts redirect to `ancora-gray.vercel.app` | The owner reached the app through a deployment URL (behind Vercel SSO) and the relayer refused its Origin; same-origin is always ours, and one canonical host keeps passkeys on one RP ID | Listing every alias; no redirect |
| 2026-10-25 | Site default is the Stellar testnet; sample data is the automatic backup | The product should be judged on-chain; the fallback and the Settings switch keep the demo safe | Sample by default with an opt-in |
| 2026-10-25 | One passkey per person, one contract per organization: a person is an OpenZeppelin smart account (its address is the "ancora ID"), an organization is our own `ancora_organization` Soroban contract (USDC, OZ AccessControl roles, approval engine, requests), and one `ancora_registry` indexes profiles and memberships | The user asked for people who hold several positions in several organizations with one passkey. Soroban's direct-invoker rule lets the person's account authorize calls on the organization and the organization authorize token transfers and registry updates, without nested delegation. The organization contract can enforce the rules itself; an OZ policy on a shared smart account could not express tiers, four-eyes and objection windows | One OZ smart account per organization with one passkey per member (the task-4 design: passkeys were per organization, the rules stayed in the app); a shared multisig with the person's passkey added per organization (nested auth, no on-chain rules) |
| 2026-10-25 | The rules are a declarative policy document (canonical JSON, `app/shared/policyDocument.ts`) compiled into the contract's `Policy`; the contract stores the document's SHA-256 at creation and with each rule change | Anyone can verify that the readable rules match what the contract enforces; the hash is cheap on-chain, the document is reproducible from the contract state | Storing the document on-chain (rent); no verification |
| 2026-10-25 | Follow stellar-registry/perch's idea (declarative policy IR lowered onto OZ stellar-accounts) without depending on it; stock OZ policies where they fit (cumulative crew limits through `spending_limit` installed on the organization's context in task 9), custom rules in the organization contract where they don't | Perch's constraints are per call; approvals with tiers and objection windows need state the organization contract owns anyway. The OZ `Policy` trait only needs `smart_account.require_auth`, which the organization contract satisfies as direct invoker, so stock policies extend our rules later | Building on perch now (early project, Apache-2.0); re-implementing spending limits |
| 2026-10-25 | Profiles on-chain in the registry (name ≤ 64 bytes, picture URL ≤ 256 bytes); pictures are 256×256 WebP in Vercel Blob at `avatars/<sha256>.<ext>` (public, content-addressed, immutable), uploaded without login; only the owner's passkey can point their profile at a URL | A profile must follow the person to every device and organization; the image itself is too large for on-chain storage; content addressing makes uploads idempotent and uninteresting to abuse | Data URLs on-chain (rent); browser-only profiles; an account database |
| 2026-10-25 | Personal settings (profile, theme, expert mode, install, data source) live on the person's page `/app/me` ("your pass"); `/app/settings` is the organization's (logo, on-chain facts) | Two subjects, two pages; the pass doubles as the thing you show to get invited (ID, QR) | One mixed settings page |
| 2026-10-25 | Recovery ("Lifeline") goes through a dedicated recovery contract that is the only thing authorized on the account for signer changes, with a waiting period and cancel-by-any-signer; it can never move money | OZ context rules scope by contract, so guardians must not get a rule on the account itself; a delay plus cancel keeps a compromised guardian set from taking over silently | Guardians as direct signers; social recovery without delay |
| 2026-10-25 | "Send now": a fully approved request whose objection window has passed is executed by the operator on request from any member; the contract re-checks everything, the operator cannot create, approve or alter requests | Nobody should have to pay or sign to let an approved payment leave; the operator already sponsors fees | Requiring a member's passkey for execution; a cron job |
| 2026-10-26 | Several stablecoins per organization: the organization contract holds a list of accepted tokens, each tagged with the fiat currency it stands for; balances and committed amounts are per token; payments name their token; accepting or dropping a token is a governance change (dropping needs a zero balance and no open request) | The user wants organizations that accept several stablecoins (Circle USDC, BlendUSDC, later EURC and more) rather than one per organization; the contract already took its token at creation, so the list was the natural extension | One token per organization chosen at creation; one organization per asset |
| 2026-10-26 | The rules are written in one home currency per organization (EUR or USD, part of the policy document); a payment in an accepted token of another currency takes the strictest tier plus the seal | Tiers in two currencies would double the rules UI, and silently equating €1 with $1 would misapply the tiers; "strictest until a rate exists" can never under-approve. A live FX rate from the Reflector oracle (SEP-40) is the follow-up | Tiers per currency; fixed parity; oracle now (risk of a testnet oracle outage blocking payments) |
| 2026-10-26 | The assets an organization may accept come from an operator allowlist (`ORG_ASSETS`: symbol, contract, currency), resolved by the setup script; on testnet BlendUSDC and Circle's USDC | Keeps the demo to tokens with a faucet and a known issuer; any Stellar asset contract works in the contract itself, so adding EURC is one config line | Free-form token addresses in the UI (typos, scam tokens) |
| 2026-10-26 | Circle USDC test float is filled by hand at faucet.circle.com; `test-money` grants shrink to a tenth of what is left when the float runs low | Circle's faucet is captcha-gated, so the script can only add the trustline and report; adaptive grants keep many demos possible from one top-up | Dropping Circle USDC; a bigger manual float |
| 2026-10-26 | Non-fungible holdings (membership cards, certificates) are an outlook item, not built: the asset list is typed for fungible tokens today | The asset model (token address + what it stands for) extends to OZ NonFungible contracts, but the rules engine compares amounts, which NFTs don't have | Modeling NFTs now |
| 2026-10-26 | The Reserve is the organization contract depositing into the asset's DeFindex vault itself: it pre-authorizes the vault's token pull with `authorize_as_current_contract` (one sub-invocation: `token.transfer(org, vault, amount)`), and withdraws by burning the shares worth the requested amount (rounded up, 1% tolerance on the amount received) | The organization is a contract, so it can't sign; Soroban's invoker auth covers the direct vault call and the explicit sub-invocation covers the nested transfer, nothing else. Rounding happens in the vault's share math, so the withdrawal asks for at least 99% and the UI reads the exact value back | Depositing through the person's account (would make the person the vault depositor); a separate treasury contract |
| 2026-10-26 | Earnings shown as vault value minus principal moved in (tracked per token in the organization contract); no APY figure on testnet | The vault reports value per share, not a rate; Blend's rate varies and the vault takes fees, so the honest number is what the organization would get back today versus what it put in | Quoting a rate from Blend's pool; the sample data's fixed simulated rate |
| 2026-10-26 | A vault is part of the asset's allowlist entry (`Symbol:token:currency[:vault]`), fixed when the asset is accepted | Which vault an asset earns in is a trust decision the operator makes per deployment, and the organization accepts it together with the asset through governance | A vault registry; founder-chosen vaults |
| 2026-10-26 | The security seal's quantum-safe check is an in-contract ML-DSA-44 verifier (`fips204` 0.5, no_std, stack-only) behind OpenZeppelin's external-verifier interface (`verify(payload, key, sig)`, `canonicalize_key`) | Testnet runs protocol 29, which has no ML-DSA host function; FIPS 204 in pure Rust compiles to 15 KB of WASM and verifies within the testnet limits (checked by invoking it on-chain). ML-DSA-44 is the smallest parameter set (1,312-byte key, 2,420-byte signature) and already gives 128-bit post-quantum security; the interface is OZ's, so a person's smart account can list the key as a signer once the key management lands. The native host function (Protocol 30 "Bell") replaces the body of `verify` without changing callers | ML-DSA-65 (larger signatures, more CPU); waiting for the host function; a server-side check (not non-custodial) |
| 2026-10-26 | Test vectors for the seal come from `@noble/post-quantum` (the library the app will use on the device) and live in `contracts/test-vectors/ml-dsa-44.json` | Proves interoperability between the signer the browser will use and the verifier on-chain, in the same place as the rules vectors | Rust-generated vectors only |
| 2026-10-26 | Funding from a person's own wallet goes through Stellar Wallets Kit (Freighter, Hana, xBull, Albedo modules only), with ancora building the token `transfer(wallet → organization)` invocation and the wallet signing it | Wallets' plain "send" is a classic payment, which cannot target a contract address (the user hit this with Hana); building the Soroban invocation ourselves works with every wallet that can sign a transaction. The kit is the ecosystem standard for wallet connections; only four modules are imported so hardware-wallet and WalletConnect SDKs stay out of the bundle, and the whole module loads on demand | Telling people to use Freighter only; a deposit address per person (custodial); SEP-24 ramps for crypto deposits |
| 2026-10-26 | The organization logo is a URL on the organization contract (`set_logo`, top role, no approval request) pointing at the same content-addressed image store as profile pictures | A logo is cosmetic and should follow the organization to every device; the top role already owns the organization's profile in the app; reusing the image store keeps one upload path | Logo changes as governance requests; logos in the registry |
| 2026-10-26 | Discussion threads are append-only files in Vercel Blob (`discussions/<org>/<request>/…`: one file per entry, reaction and "answered" mark); `/api/discussions` checks that the organization is ancora's and that the author is a member by reading the contract, but entries are not signed by the passkey yet | Text should stay private to the organization and off the public ledger; one file per fact avoids lost updates when two people post at once; Blob is already the one off-chain store. Signing entries with the person's account (SEP-53 message signing through the kit) is the follow-up that makes authorship provable | A database; comments on-chain; no membership check |
| 2026-10-26 | Spending limits live in the organization contract (`SetSpendingLimit` governance change, rolling window per member, checked in `propose_payment`), not in OpenZeppelin's `spending_limit` policy | OZ's policy guards a smart account's own token transfers through its context rules; since the identity pivot the money sits in the organization contract, which is not a smart account, so the allowance has to be part of its rules.
